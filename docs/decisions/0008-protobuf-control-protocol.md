# ADR-0008: Protobuf Control Protocol

| Field | Value |
|---|---|
| Status | Accepted |
| Date | 2026-08-09 |
| Owners | Architecture discussion |

## Context

Every peer must exchange enrollment, peer state, resource, model, and inference commands. The format must work on Windows, Linux, and macOS and must evolve without tying the protocol to Rust memory layouts.

## Decision

Use Protocol Buffers generated by `prost` for control messages.

Frame each Protobuf envelope with a four-byte big-endian length on the long-lived bidirectional QUIC control stream. Limit a control frame to 1 MiB. Move large bytes on separate QUIC streams.

Start at protocol `1.0`. Reject different major versions. Negotiate the highest shared minor version. Never reuse a Protobuf field number.

Canonical contract: [Control protocol](../architecture/protocol/control-protocol.md)

## Rejected: Rust-native serialization

Formats that encode Rust enums or structs directly can make the first implementation shorter. They also make schema evolution depend on Rust representation and library behavior. That is the wrong boundary for a protocol used by independently updated peers.

## Rejected: JSON control messages

JSON is easy to inspect but larger, slower to parse, and weaker for fixed binary identifiers. Diagnostics can render typed messages as JSON without making JSON the wire format.

## Rejected: Protobuf for model and tensor bytes

Wrapping large byte arrays in Protobuf adds avoidable buffering and copies. Model artifacts and activation tensors use dedicated streams and formats.

## Consequences

- `.proto` files become reviewed source files.
- `prost-build` runs during the build or generated output is produced by a controlled build step.
- Unknown fields are skipped and not preserved by Prost. Messages must never be decoded and re-encoded for forwarding.
- Message lengths, identifier lengths, and domain state still require explicit validation after decoding.
