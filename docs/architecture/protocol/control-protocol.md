## Boundary

Control messages describe mesh state and actions. Model weights, activation tensors, and other large byte payloads do not travel inside control messages.

Use Protocol Buffers generated by `prost`. The checked-in `.proto` files are the wire source of truth. Generated Rust files are build output and are not edited.

## Control stream framing

Every peer connection owns one long-lived bidirectional QUIC control stream.

Each control frame is:

```text
0               4                                      4 + N
+---------------+------------------------------------------+
| N: u32 BE     | Protobuf ControlEnvelope: N bytes        |
+---------------+------------------------------------------+
```

Rules:

- `N` is an unsigned 32-bit length in network byte order.
- `N` must be between 1 and 1,048,576 bytes.
- One frame contains exactly one `ControlEnvelope`.
- The control stream is not compressed.
- Readers use exact-length reads. QUIC chunks are not message boundaries.
- A malformed or oversized frame closes the peer connection with a protocol error.
- Large data uses a separate QUIC stream so it cannot block health and cancellation messages.

## Envelope

The first schema is logically:

```proto
syntax = "proto3";
package mesh.v1;

message ControlEnvelope {
  uint32 protocol_major = 1;
  uint32 protocol_minor = 2;
  bytes message_id = 3;
  bytes sender_node_id = 4;
  optional bytes in_reply_to = 5;

  oneof body {
    Hello hello = 10;
    Welcome welcome = 11;
    PeerUpdate peer_update = 12;
    Heartbeat heartbeat = 13;
    ErrorMessage error = 14;
    CapabilityReport capability_report = 15;
    BenchmarkRequest benchmark_request = 16;
    BenchmarkAccept benchmark_accept = 17;
    BenchmarkReject benchmark_reject = 18;
    BenchmarkResult benchmark_result = 19;

    ResourceQuery resource_query = 20;
    ResourceOffer resource_offer = 21;
    ReserveRequest reserve_request = 22;
    ReserveAccepted reserve_accepted = 23;
    ReserveRejected reserve_rejected = 24;
    ReservationCommit reservation_commit = 25;
    ReservationRelease reservation_release = 26;

    ModelPrepare model_prepare = 30;
    ModelProgress model_progress = 31;
    ModelReady model_ready = 32;
    ModelFailed model_failed = 33;

    InferenceRequest inference_request = 40;
    TokenResult token_result = 41;
    CancelRequest cancel_request = 42;
  }
}
```

Initial invariants:

- `protocol_major` is `1`.
- `protocol_minor` starts at `0`.
- `message_id` is exactly 16 random bytes and is unique per sender process.
- `sender_node_id` is exactly 32 bytes.
- `in_reply_to`, when present, is exactly 16 bytes.
- Exactly one `body` value must be present.
- Every string must be valid UTF-8 and respect its message-specific limit.
- Every receiver validates lengths and state before acting.

The message names above are reserved. Adding fields or new `oneof` cases is compatible within the same major version. Field numbers are never reused.

## First enrollment messages

`HELLO` and `WELCOME` are the first implemented messages.

```proto
message Hello {
  bytes mesh_id = 1;                    // exactly 16 bytes
  uint32 minimum_protocol_minor = 2;
  string display_name = 3;              // 1..128 UTF-8 bytes
  optional bytes enrollment_id = 4;     // exactly 16 bytes
  optional bytes enrollment_secret = 5; // exactly 32 bytes
  bytes capability_digest = 6;          // exactly 32 bytes
  repeated EndpointCandidate candidates = 7; // at most 32
}

message Welcome {
  uint32 selected_protocol_minor = 1;
  PeerRecord responder = 2;
  repeated PeerRecord known_peers = 3;
}
```

Rules:

1. The joining peer opens the control stream and sends `HELLO`.
2. The receiving peer validates the envelope, Mesh ID, certificate binding, invitation, and version.
3. The receiving peer validates and atomically binds a valid invitation to the joining certificate's Node ID.
4. `WELCOME` selects one minor protocol version and returns the inviter plus known peers. Permanent peer state and invitation consumption are one local transaction.
5. A reconnect sends `HELLO` without enrollment fields and must match an existing peer record.
6. A rejected handshake sends an error when possible, then closes the connection.

## Capability and benchmark messages

After a successful handshake, peers exchange `CapabilityReport` and may run directional delay and bandwidth probes. Exact measurement rules, age windows, stability scoring, and placement thresholds are canonical in [Network benchmark and placement cost](../networking/network-benchmark.md).

Bandwidth payloads use a separate unidirectional QUIC stream with a fixed 32-byte `MSHB` header. They never travel inside control frames.

## Compatibility

Use semantic wire compatibility, not application-release compatibility.

- Different protocol major versions cannot connect.
- Peers with the same major select the highest minor version supported by both.
- A peer must not send a field or message behavior that requires a minor version newer than the selected version.
- Prost skips unknown fields while decoding. A peer must not decode and re-encode another peer's message as a forwarding mechanism because skipped fields are not preserved.
- Unknown `oneof` cases and unknown enum values are not treated as their zero value. They produce an unsupported-message error unless the containing message defines them as optional.
- Capability fields decide optional behavior. Application version strings never decide protocol behavior.

## Error contract

Every control failure uses an `ErrorMessage` when the control stream is still usable:

```proto
message ErrorMessage {
  ErrorCode code = 1;
  optional bytes related_message_id = 2;
  bool retriable = 3;
  string summary = 4;
  string detail = 5;
  optional bytes deployment_id = 6;
  optional bytes request_id = 7;
  optional uint64 transfer_id = 8;
}

enum ErrorCode {
  ERROR_CODE_UNSPECIFIED = 0;
  MALFORMED_FRAME = 1;
  UNSUPPORTED_PROTOCOL = 2;
  IDENTITY_MISMATCH = 3;
  MESH_MISMATCH = 4;
  INVITE_INVALID = 5;
  INVITE_EXPIRED = 6;
  INVITE_ALREADY_USED = 7;
  UNKNOWN_PEER = 8;
  INVALID_STATE = 9;
  RESOURCE_BUSY = 10;
  RESERVATION_REJECTED = 11;
  MODEL_PREPARATION_FAILED = 12;
  REQUEST_REJECTED = 13;
  TRANSFER_REJECTED = 14;
  CANCELLED = 15;
  INTERNAL = 16;
}
```

- `summary` is a safe user-facing sentence of at most 512 UTF-8 bytes.
- `detail` is an optional technical description of at most 4,096 UTF-8 bytes.
- Optional deployment and request IDs are exactly 16 bytes. Activation errors include the request and transfer IDs when known.
- Errors never include provider tokens, private keys, local file contents, or raw model data.
- `ERROR_CODE_UNSPECIFIED` is never sent.
- A receiver treats an unknown error code as `INTERNAL` and keeps the numeric value in diagnostics.

## Time and identifiers

- Durable IDs use fixed-size random bytes, not timestamps.
- Protocol timestamps are signed Unix milliseconds in UTC only where wall time is required.
- Lease and timeout durations are unsigned milliseconds.
- Local timeout measurement uses a monotonic clock.
- A sender cannot extend a reservation by changing its wall clock.

## Initial connection limits

- Enrollment handshake deadline: 10 seconds after QUIC connection establishment.
- Control write deadline: 10 seconds per frame.
- QUIC keep-alive interval: 15 seconds while connected.
- QUIC idle timeout: 60 seconds.
- A request-specific deadline overrides the general control deadline when it is shorter.

These are operational defaults. Changing them does not change the wire schema.

## Ownership

- `.proto` files belong to `mesh-core`.
- Framing, limits, and QUIC stream handling belong to `mesh-net`.
- Domain crates validate whether a decoded command is legal in their current state.
- The GUI never constructs or parses protocol frames.
