Architecture 01

Decentralized node foundation

PCs in different locations communicate directly. Every PC runs the same modules. There is no gateway, relay, or permanent controller.

Current boundary

This step covers node discovery, direct connections, hardware reporting, and temporary job ownership. LLM inference and model training come later.

Module responsibilities

Each module owns one clear part of the node. This list will grow as the architecture grows.

ID
Module
What it does
Important rule
M01
Node Connectornode_connector
Starts all node modules. Receives messages from direct links. Sends each message to the correct module.
It is not a master. Every PC runs its own connector.
M02
Peer Storepeer_store
Stores the mesh ID, known peer IDs, last known addresses, and current connection state.

M03

Tries IPv6, IPv4, automatic port opening, and hole punching. Keeps working connections alive.
No relay is used. A blocked peer is reported as unavailable.
M04
Hardware Scannerhardware_scanner
Reads GPU type, GPU memory, CPU, system memory, and basic network information.
Hardware data is refreshed when the node starts or its hardware changes.
M05
Node Statenode_state
Keeps the node's current hardware, peer links, active jobs, and local health in one local state.
Each PC owns its state. There is no central copy.
M06
Job Managerjob_manager
Creates a job, selects peers, splits the work, tracks progress, and combines returned results.
The creator owns only that job. It does not control the mesh.
M07
GPU Workergpu_worker
Accepts one work part from the Job Manager and runs it on the local GPU.
It reports progress and returns the result to the job owner.

04 — NET

Direct internet links

The Node Connector tries each direct method in order. It stops when one works.

Connection order

  1. Use a reachable public IPv6 address.
  2. Use a reachable public IPv4 address.
  3. Ask the router to open a port with UPnP or NAT-PMP.
  4. Have both PCs send packets and attempt hole punching.
  5. Mark the peer unavailable when every method fails.

Hard network limit

Some routers and internet providers block every direct method. Software cannot always create a direct path through them.

This is a network routing limit. It is not an encryption problem.

No relay means no fallback. Two blocked PCs cannot communicate and remain unavailable to each other.

06 — ADR

Current decisions

Agreed boundaries for this architecture step.

Accepted
Topology
Every PC is an equal peer. There is no permanent master.
Accepted
Communication
PCs move work and results through direct internet connections.
Rejected
Public server
The architecture will not depend on a public gateway, coordinator, or relay.
Accepted
Discovery
A new PC joins with an invite from one known peer, then learns the remaining peers.
Accepted
Job control
The job creator becomes the temporary owner of that job only.
Deferred
Compute method
LLM inference and model-training execution are outside this step and will be designed later.
